Application access-layer constraint

The backend currently creates a service-role @supabase/supabase-js client and calls db.from(...) and db.rpc(...) throughout the services, routes, auth, billing, research, blogs, and assessment workers. The current package has no PostgreSQL driver. Changing SUPABASE_DB_URL to an RDS URL will therefore not switch the app over.

Recommended: native PostgreSQL adapterIntroduce pg (or a chosen query layer), port each query/RPC, recreate authorization in the API, and remove the Supabase service-role dependency after parity tests. This is the cleanest long-term RDS design.
Transitional: self-host an API compatibility layerRun PostgREST or a small adapter beside the app and point the existing client at it. This reduces first-cutover code churn but adds another service, key management, and a need to reproduce the current RLS/service-role behavior.

Decision required before implementation. The database restore can proceed in parallel, but application cutover cannot be considered complete until one access strategy is tested end-to-end.

Migration sequence

1

Freeze the source of truth

Confirm the Supabase project, maintenance window, data-retention requirements, and whether Supabase Auth, Storage, Realtime, or only the application-owned public schema is in scope. Record a final live catalog snapshot and checksum.

2

Capture live DDL and DML

Run the commands below from a host that can reach Supabase. Dump public only unless a separate decision explicitly includes managed schemas. Store dumps encrypted; they contain user, token, billing, and research data.

3

Provision RDS and private networking

Create a DB subnet group across two AZs, an RDS security group that trusts only the EC2 SG, a PostgreSQL parameter group with SSL enforcement, encryption, backups, deletion protection, and a Secrets Manager secret. Validate connectivity from EC2 before restoring data.

4

Restore and validate schema

Restore the live DDL, required extensions, functions, constraints, indexes, sequences, and RLS flags. Do not restore Supabase ownership, managed roles, or Supabase internal schemas. Create a least-privilege application role.

5

Restore data and replay deltas

Load the data-only dump, reset sequences, compare exact counts and checksums, and run foreign-key/orphan checks. For low downtime, take a final delta dump during the maintenance window; otherwise schedule a short write freeze.

6

Port the application access layer

Implement the selected native adapter or compatibility layer, move the DB secret into the EC2 runtime, and test auth, DSA/LLD/HLD content, assessments, blogs/bookmarks, research jobs, billing webhooks, email workers, and scheduled jobs against RDS.

7

Shadow, cut over, observe

Run read-only parity checks, measure p50/p95/p99 database latency, enable RDS Performance Insights/Enhanced Monitoring, switch writes, and keep Supabase read-only for the agreed rollback period.

8

Retire only after the rollback window

Rotate old Supabase credentials, export the final audit artifacts, remove unused Supabase dependencies, and decommission the old database only after backups and business-owner sign-off.

Live capture commands

These are templates. Load the password from a secret manager or a protected shell environment; never put it in source control, the command history, or this HTML.

# Run from a controlled migration host
export SUPABASE_DB_URL='<live Supabase direct/session URL>'
mkdir -p /secure/optimus-migration

# Live DDL: application schema only
pg_dump "$SUPABASE_DB_URL" \
  --schema=public --schema-only --no-owner --no-privileges \
  --file=/secure/optimus-migration/public-schema.sql

# Live DML: custom format for resumable restore
pg_dump "$SUPABASE_DB_URL" \
  --schema=public --data-only --no-owner --no-privileges \
  --format=custom --file=/secure/optimus-migration/public-data.dump

sha256sum /secure/optimus-migration/public-schema.sql \
          /secure/optimus-migration/public-data.dump

The captured live schema was 1,478 lines and contained 22 tables plus 4 public functions. The observed data dump was about 1.2 MiB compressed. Treat those figures as a baseline, not a replacement for a final cutover dump.

RDS provisioning templates

Use placeholders and review every value. The requested db.t4g.micro is Graviton/Arm-based but has only 1 GiB RAM; db.t4g.small is the safer starting point for a production API if the budget allows.

REGION=ap-south-1
VPC_ID=vpc-0dfc5b1580f85feb9
APP_SG_ID=sg-081d1dcdd15800cfa
DB_SG_ID=<new RDS security-group-id>

aws ec2 authorize-security-group-ingress \
  --region "$REGION" --group-id "$DB_SG_ID" \
  --protocol tcp --port 5432 --source-group "$APP_SG_ID"

aws rds create-db-subnet-group \
  --region "$REGION" --db-subnet-group-name optimus-rds-private \
  --db-subnet-group-description "Optimus PostgreSQL private subnets" \
  --subnet-ids <ap-south-1a-subnet> <ap-south-1b-subnet>

aws rds create-db-instance \
  --region "$REGION" --db-instance-identifier optimus-prod \
  --engine postgres --engine-version 17 \
  --db-instance-class db.t4g.micro \
  --allocated-storage 20 --storage-type gp3 \
  --master-username optimus_admin \
  --manage-master-user-password \
  --db-name optimus --port 5432 \
  --db-subnet-group-name optimus-rds-private \
  --vpc-security-group-ids "$DB_SG_ID" \
  --no-publicly-accessible \
  --backup-retention-period 7 \
  --storage-encrypted --deletion-protection \
  --copy-tags-to-snapshot

Prefer an explicitly approved KMS key, parameter group (rds.force_ssl=1), CloudWatch log exports, and a maintenance window. Store the generated master secret in Secrets Manager and create a separate least-privilege app role after restore.

Restore commands

export RDS_ADMIN_URL='<temporary admin URL from Secrets Manager>'

# Check extensions before restore; install only what the live public DDL needs
psql "$RDS_ADMIN_URL" -v ON_ERROR_STOP=1 -c \
  'create extension if not exists pgcrypto;'

psql "$RDS_ADMIN_URL" -v ON_ERROR_STOP=1 \
  --file=/secure/optimus-migration/public-schema.sql

pg_restore "$RDS_ADMIN_URL" \
  --data-only --no-owner --no-privileges \
  /secure/optimus-migration/public-data.dump

# Generate sequence resets from live ownership metadata (UUID tables are ignored)
psql "$RDS_ADMIN_URL" -Atc <<'SQL' | psql "$RDS_ADMIN_URL" -v ON_ERROR_STOP=1
select format('select setval(%L, coalesce(max(%I), 1), true) from %I.%I;',
  seq.oid::regclass::text, att.attname, ns.nspname, tbl.relname)
from pg_class seq
join pg_namespace ns on ns.oid = seq.relnamespace
join pg_depend dep on dep.objid = seq.oid and dep.deptype = 'a'
join pg_class tbl on tbl.oid = dep.refobjid
join pg_attribute att on att.attrelid = tbl.oid and att.attnum = dep.refobjsubid
where seq.relkind = 'S' and ns.nspname = 'public';
SQL

The sequence query uses live ownership metadata and ignores UUID-backed tables. Restore extensions and functions before data-dependent validation, then apply grants and the app role.

Validation gates before switching traffic

  • Exact row counts match for all 22 public tables.
  • Primary keys, unique indexes, foreign keys, checks, and four RPC functions exist.
  • All sequences/UUID defaults generate new values without collisions.
  • RLS posture and API authorization are equivalent after the adapter change.
  • Users can sign in, refresh tokens, use Google auth, and update profiles.
  • DSA, LLD, HLD, assessments, code execution, blogs, likes, and bookmarks work.
  • Research jobs, workers, invoices, Dodo webhooks, and reminder emails are idempotent.
  • Payment rows and webhook event history are present and no duplicate events are created.
  • p50/p95/p99 database latency, error rate, CPU, connections, and storage are observed.
  • Backups restore into a disposable instance and the final dump checksums are archived.

Rollback

If parity or error-rate gates fail, stop writes to RDS, point the adapter back to Supabase, and replay only the approved delta or restore from the final source snapshot. Keep Supabase credentials active until the business-owner rollback window expires. Never delete the Supabase project as part of the first cutover.

Post-cutover follow-ups

The migration is live. Keep these operational decisions visible:

  1. Monitor the 1 GiB db.t4g.micro; move to db.t4g.small if connection pressure or memory warrants it.
  2. Keep RDS private and retain the EC2 security-group-only ingress rule.
  3. Complete the agreed Supabase rollback window before revoking its credentials.
  4. Supabase Auth/Storage/Realtime remain out of scope unless separately replaced.
  5. Archive the dump checksums and restore/parity logs, then delete sensitive dump files.
