Private Judge0 CE deployment plan

Deploy an open-source Judge0 Community Edition service beside the Optimus API, connect the existing Judge0 adapter through a private AWS path, and use Muse-Spark only for assessment question generation—not for code execution.

Recommendation

Self-host Judge0 CE

The backend already speaks Judge0’s API, so the production change is primarily infrastructure plus environment configuration.

2. What is already implemented

Keep the application contract stable.

Existing Optimus integration

  • src/services/runner/judge0.js posts base64-encoded submissions and reads Judge0 responses.
  • Concurrency limiting, retry/backoff for 429/5xx, request timeout, and short dedupe caching are present.
  • CPU, wall-clock, memory, and network-off limits are sent per execution.
  • Assessment verification runs generated reference questions before they enter the bank.
  • Production environment is encrypted in SSM and refreshed by the existing GitHub Actions workflow.

Current language scope

  • Python, JavaScript, Java, and SQLite are wired in the application.
  • Judge0 CE supports C++, but Optimus does not expose C++ yet; add it as a separate application change.
  • LLD is the primary machine-coding path. HLD is mainly knowledge/MCQ; data-oriented HLD may use SQL.
  • Keep the first deployment focused on infrastructure and the currently supported language set.

4. Implementation sequence

Deploy in small, reversible increments.

Confirm prerequisites and capacity

  • Confirm AWS account, region ap-south-1, VPC, subnet, and whether a NAT path already exists for image pulls and package updates.
  • Choose a dedicated runner size: start at least with 2 vCPU / 4 GiB RAM and 30–40 GiB encrypted gp3 storage; scale from queue and memory metrics.
  • Pin a vetted Judge0 CE release and record the exact release/compose revision used for rollback.
  • Generate JUDGE0_AUTH_TOKEN and Judge0’s internal database/password secrets outside Git.

Provision the isolated AWS runner

  • Extend infra/backend.yml or add a runner stack with a dedicated security group and EC2 instance.
  • Allow inbound Judge0 traffic only from the Optimus API security group; do not open port 2358 to the internet.
  • Attach SSM managed-instance permissions and use SSM for administration; do not add an SSH ingress rule.
  • Install Docker/Compose and configure the cgroup mode required by the pinned Judge0 release. Reboot if the release requires it.
  • Persist Judge0 Postgres/Redis data on encrypted storage and configure restart-on-failure.

Deploy Judge0 CE and lock it down

  • Run the official Judge0 compose stack using the pinned version and private secrets.
  • Verify the API listens on the private interface and that its authentication token is required.
  • Verify network access is disabled for submitted programs and that CPU, wall-clock, memory, output, and process limits are active.
  • Smoke-test an allowed program, compile failure, timeout, memory limit, and rejected unauthenticated request.

Connect Optimus through SSM

Merge the environment values into the encrypted OPTIMUS_PROD_ENV repository secret, then let the existing workflow sync SSM and restart the API.

  • Start with ASSESSMENT_BANK_TOPUP=false while validating the provider contract and runner.
  • Generate one LLD question manually, confirm reference verification, then enable the background bank worker.
  • Monitor LLM usage separately from Judge0 usage. A Muse-Spark outage must not make the code runner unavailable.

5. Acceptance tests

Deployment is complete only when these pass.

Security and isolation

  • Judge0 port is unreachable from the public internet.
  • Missing or incorrect auth token is rejected.
  • Submitted code cannot reach the network or read host files.
  • API service-role/database secrets are not mounted into Judge0 containers.
  • SSM, CloudWatch, and application logs do not print source code or token values.

Product behavior

  • Python, JavaScript, Java, and SQLite sample runs return expected output.
  • Compile errors and runtime errors are shown as useful assessment feedback.
  • Timeout and memory failures finish within the API timeout budget.
  • Hidden tests grade correctly and assessment state is persisted.
  • Repeated Run presses are deduplicated and concurrent users respect the configured gate.

6. Operations, cost, and rollback

Make failure safe and visible.

Operations checklist

  • Alert on runner health failure, Docker/container restart loops, disk pressure, queue growth, and repeated 5xx/timeout responses.
  • Record Judge0 release, instance ID, private address, EBS snapshot policy, and secret rotation date.
  • Rotate the shared auth token by updating Judge0 and Optimus together through a controlled maintenance window.
  • Review CPU/memory limits and concurrency after observing real assessment traffic.

Cost envelope

Judge0 CE software is open source and has no per-submission fee when self-hosted. AWS cost is the dedicated compute instance, encrypted gp3 storage, outbound traffic, and—if required by the subnet—NAT gateway charges.

Use the smallest runner that passes the acceptance tests, but do not place it on the existing t3.micro API host. A 2 vCPU / 4 GiB starting point is a capacity recommendation, not a fixed AWS price; validate the current ap-south-1 rate in the AWS calculator.

Rollback order

  1. Set CODE_RUNNER_ENABLED=false and restart Optimus if the runner must be disabled immediately; coding assessments fail closed rather than executing elsewhere.
  2. For an endpoint-only rollback, restore the previous JUDGE0_URL, header, and key in SSM, then restart the API.
  3. Stop or isolate the Judge0 instance without deleting its encrypted data volume.
  4. Re-run the smoke suite before re-enabling live assessment traffic.
Fallback caveatThe public ce.judge0.com endpoint has no SLA and may impose limits. Treat it as a temporary emergency fallback, not the production architecture.
